## What this run proves (ALM-51)

- **The harness is recorded once.** Bootstrap ran `aos-cap harness set hermes`:
  `.aos/harness.yml` = `{harness: hermes, sheet: <render>/reference/harness-hermes.md,
  cli: ~/.local/bin/hermes}`.
- **The render keeps one sheet.** `personal/` and the front agent's
  `skills/capability-lifecycle/reference/` hold `harness-hermes.md` and `no-cheatsheet.md` only;
  `full-install.yaml` forbids the other five.
- **`cron` everywhere.** The lockfile writes `cron_owned` (kb 3 ids, work-tracker 1); manifests
  read `cron:`/`expr:`.
- **`session` installs as a dependency.** The case install pulled `session` 0.1.0 in first: the
  `aos-session` tool in `<sandbox>/uv`, its skill in the main agent.
- **The delivery reaches the session that asked.**
  - Session A (the operator's invite chat in `aos-test`) minted the invite with
    `ref: <subject>--<A>`; the gateway created session B in the interviewer titled
    `aos-invite:<subject>--<A>` (source `aos-ui`).
  - After the guest approved, the post-hook — run by the dashboard backend, not a login shell —
    started the runner. It opened `guest-synthetic-guest ingest — <subject> 01:04` in the
    archiver, which wrote `summary-<subject>.md` and `delivery-<subject>.md`, then continued
    session A: 13 → 19 messages, the delivery page as the new user turn. `.close-notice.log`
    stayed empty. Session A came from the CLI and was never marked read, so its empty
    `last_read_at` reads as *read* in Hermes (NULL = read) — unread is shown in the probe below.
- **A gone session opens a new one, and nothing else.** A throwaway session was deleted, then
  notified: `Session <id> is gone; opened "e2e notice 01:12"`. Sessions 7 → 8 — the continue
  attempt created none.
- **No PATH dependency.** `open` and `notify` ran with `PATH=/usr/bin:/bin`: `aos-session` used
  the recorded `cli`.
- **Opening lines are not orders.** See finding 2.

## Findings

1. **A job came due before the snapshot.** The fixture's steward hour (22:47 Lisbon) fell three
   minutes after the Day-N install ended. The job was paused at once, ahead of PROTOCOL step 5's
   order; the backend ticks crons without the profile `.env`, so a run would have acted on `~/aos`.
   Its pre-pause `cron/jobs.json` was saved first, and `steward/` was normalized from a copy of the
   profile carrying that file, so the snapshot records the job as installed.
2. **An imperative opening line triggered the `session` skill.** `aos-session open` with the
   ghostwriter line `Open this week's editorial session.` in `aos-test` (which has the `session`
   skill and no ghostwriter skill): the agent read the line as an order and opened a second
   session. The `session` skill's description begins "Opens one new titled session". Ghostwriter's
   cron session also carries that skill (its profile links it to open sessions), so the personal
   ghostwriter lines became noun phrases — `This week's editorial session.`,
   `This week's source interview.`. Re-run with the noun phrase: one session, none opened by the
   agent.
3. **The case's aos-ui invite step returns a masked link** (pre-existing, not ALM-51). Hermes masks
   token-shaped strings in tool output, so the agent saw `#invite=` plus a 13-character
   placeholder and could not hand the link over. The invite is a stateless signed token, so the
   operator re-minted the same request body (same ref, so the same session B) with curl and kept
   the URL in a mode-600 scratch file, deleted after the run. Artificial Thoughts' own guest skill
   avoids this by printing only a short link.
4. **Root `config.yaml` changed during removal, by other work.** Between 01:14:55 and 01:16:17
   every profile's `config.yaml`, in alphabetical order, got one new line — the AOS UI platform
   note — with a `config.yaml.bak-aosnote-20261021` beside the root file. The removal transcript
   shows no such call; other sessions were working on aos-ui on this machine. The sweep also hit
   the test `aos-test`, so after the restore that one line was re-applied to the restored profile.
   Profiles, root skills and root cron job ids are identical to pre-state.
5. **Pins written during an install are claimed by it.** The watcher wrote the pin lines into
   `aos-archiver`/`aos-steward` while their installs ran; kb recorded them as `env_lines` and
   work-tracker recorded `terminal.shell_init_files` as a config key. Harmless — removal deletes
   the profile — but it is protocol noise in the lockfile. For the case profiles only the
   credential lines went in during the install.
6. **New Hermes 0.22 runtime files.** `.env.lock`, `projects.db` and
   `provider_models_cache.json` appeared in profiles; they are harness state, added to the
   normalizer's `SKIP`.
7. **The generated case did not name its artifact file** (pre-existing). The case file says
   `episode-memo.md`, but nothing the generator ships carries the name; the installer chose
   `GUEST_ARTIFACT=memo.md` and said so. Interviewer and hooks agree, so the run was unaffected.
